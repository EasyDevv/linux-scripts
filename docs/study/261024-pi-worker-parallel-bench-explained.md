# pi worker 병렬 실험, 초보자용 해석

이 문서는 "작업자(worker) 안에서 또 작업자를 띄워 병렬로 일하게 하면 빠르고 싸질까?"를 실험한 결과를 쉬운 말로 풀어 쓴 것이다. 원본 수치와 방법은 [벤치 결과](../backlog/261024-pi-worker-nested-bench.md), 설계와 결정 이유는 [계획 문서](../plan/261024-pi-worker-autonomy.md)에 있다.

## 1. 먼저 용어 네 개

| 말 | 쉬운 뜻 |
|---|---|
| 오케스트레이터 | 일을 나눠 맡기는 사람. 여기서는 Claude 본체 |
| worker (워커) | 맡은 일을 실제로 하는 작은 AI. 싼 모델(pi)이 한다 |
| `tasks` | 오케스트레이터가 워커를 **여러 명 동시에** 부르는 방법. 일 조각마다 워커 한 명 |
| `autonomy: on` | 워커가 **스스로** 또 하위 워커(subagent)를 부를 수 있게 허락하는 스위치 |

식당으로 비유하면 이렇다.

- 오케스트레이터는 홀 매니저, 워커는 주방장이다.
- `tasks`는 매니저가 주방장 네 명에게 요리를 하나씩 나눠 주는 것이다.
- `autonomy: on`은 주방장이 "내 밑에 보조 요리사를 내가 알아서 불러도 좋다"고 허락받는 것이다.

## 2. 궁금했던 것

"주방장이 알아서 보조를 불러 일을 나누면, 전체가 빨라지고 돈도 덜 들지 않을까?"

처음에는 그럴 것 같았다. 동시에 일하면 시간이 줄 테니까. 그래서 기능을 만들고 실험했다.

## 3. 실험은 어떻게 했나

같은 숙제를 여러 방식으로 시키고 시간, 비용, 성공 여부를 쟀다.

- **tests4**: 파일 4개에 대한 가벼운 테스트 작성
- **heavy4**: 파일 4개에 대한 무거운 테스트 작성(각각 10개 이상)
- **discover**: 테스트가 없는 파일이 몇 개인지 먼저 찾고, 찾은 만큼 테스트 작성(일이 몇 조각인지 **일하다가** 알게 됨)

비교한 방식은 세 가지다.

- **off**: 워커 한 명이 혼자 순서대로 한다
- **fan**: 워커 네 명을 동시에 부른다 (`tasks`와 같다)
- **leanP**: 워커가 하위 워커 네 명을 스스로 불러 나눈다 (`autonomy: on`)

같은 조건을 3번씩 돌려 가운데 값(중앙값)을 봤다. 한 번만 돌리면 운이 섞이기 때문이다.

## 4. 결과 표

| 숙제 | 방식 | 걸린 시간 | 비용 | 성공 |
|---|---|---|---|---|
| tests4 | 혼자(off) | 53초 | $0.0083 | 3/3 |
| | 동시에 4명(fan) | **42초** | $0.0163 | 3/3 |
| | 하위 호출(leanP) | 118초 | $0.0333 | 3/3 |
| heavy4 | 혼자(off) | 102초 | $0.0151 | 3/3 |
| | 동시에 4명(fan) | 100초 (48~147) | $0.0282 | 2/3 |
| | 하위 호출(leanP) | 152초 | $0.0478 | 3/3 |
| discover | 혼자(off) | 80초 | $0.0128 | 3/3 |
| | 하위 호출(leanP) | 185초 (160~399) | $0.0443 | 2/3 |

## 5. 결과를 어떻게 읽나

### 5.1 하위 워커를 스스로 부르게 하는 건 오히려 손해였다

세 숙제 모두에서 leanP가 혼자 하는 것보다 **2~2.5배 느리고 3~4배 비쌌다.** 일이 몇 조각인지 나중에 아는 discover에서도 졌다.

이유는 "준비비"다.

- 하위 워커 한 명이 일을 시작할 때마다 지시문을 읽고 도구를 챙기는 데 토큰(=돈)과 시간이 든다.
- 맡은 일이 1~2분짜리처럼 작으면, 준비하는 시간이 일하는 시간보다 길다.
- 이사 가는데 이삿짐센터 직원 네 명을 부르면 빠를 것 같지만, 방이 하나뿐이면 서로 비켜 주느라 오히려 느린 것과 같다.

그래서 `autonomy: on`을 만든 유일한 이유("일이 일하다가 드러나는 경우")가 실험으로 **입증되지 않았다.**

### 5.2 워커를 동시에 여러 명 부르는 `tasks`는 "조금 빨라지는 대신 약 2배 비싸다"

처음 한 번만 돌렸을 때는 heavy4가 189초에서 89초로 **2배 넘게** 빨라 보였다. 그런데 3번 반복하니 혼자 하는 쪽도 102초였다. 189초는 그날 운이 나빴던 값(이상치)이었다.

- 확실히 빨랐던 건 tests4 하나(53초에서 42초)이고, 그때도 비용은 2배였다.
- heavy4에서는 시간이 48초에서 147초까지 들쭉날쭉했고, 한 번은 테스트가 실패했다.

교훈은 **한 번 잰 숫자를 믿지 말라**는 것이다. 처음 숫자만 믿었다면 "병렬은 2배 빠르다"고 잘못 결론 냈을 것이다.

### 5.3 기본값은 off로 유지한다

- 대부분의 일은 워커 한 명이 혼자 하는 게 가장 싸고 안정적이다.
- 일이 **서로 독립적이고 각각 1분 이상** 걸릴 때만 `tasks`로 나눈다.
- `autonomy: on`은 꺼 두고, 정말 필요할 때만 켜는 옵션으로 남긴다.

## 6. 비용 계산 버그도 같이 고쳤다

처음에는 하위 워커가 쓴 돈이 합계에 안 들어가서 "병렬이 더 싸다"는 가짜 결과가 나왔다. 이제는 하위 워커 비용도 합쳐서 보여 준다. 예: `$0.01 (incl. 4 subagents $0.0095)`.

가계부에서 아이들 용돈을 빼고 "이번 달 지출이 적네"라고 좋아한 셈이다. 실험을 믿으려면 먼저 **재는 방법이 맞는지** 확인해야 한다.

## 7. 곁다리로 확인한 안전장치

여러 워커가 같은 파일을 동시에 고치면 서로의 작업을 덮어쓸 수 있어서 **파일 잠금(file-lock)** 을 만들었다.

- 한 워커가 파일을 고치는 동안 다른 워커의 수정은 막힌다.
- 정상 종료나 SIGTERM(정중한 종료)으로 끝나면 잠금이 풀린다.
- SIGKILL(강제 종료)이면 잠금이 남지만, 다음 워커가 "주인이 죽었네" 하고 알아서 치운다.
- 한계: `edit`, `write` 도구만 막는다. `bash`로 파일을 바꾸는 건 못 막는다. 이 점은 알고 받아들였다.

## 8. 한 줄로 요약

> 병렬은 공짜가 아니다. 일 조각이 충분히 크지 않으면 혼자 하는 게 낫고, 나눌 때는 오케스트레이터가 `tasks`로 나누는 게 낫다. 워커가 스스로 하위를 부르는 건 실험에서 한 번도 이기지 못했다.

## 9. 직접 확인하려면

```sh
cd ~/.agents/plugins/pi
bun evals/bench.ts --scenarios tests4,heavy4 --configs off,fan,leanP --runs 3
```

결과는 `~/.cache/pi-worker-evals/bench.jsonl`에 쌓인다. 실행하면 실제 모델 호출 비용이 든다(숙제 2개 × 방식 3개 × 3회 = 18번 실행, 합계 약 $0.5 안팎).

## 10. 한계

- 모델은 `deepseek-v4.1-flash:high` 하나, 숙제는 테스트 작성 위주다. 다른 모델이나 다른 종류의 일에서는 다를 수 있다.
- 반복이 3회뿐이라 중앙값도 확정이 아니라 경향이다.
- 파일 하나를 두 워커가 동시에 건드리는 상황은 실험에서 일어나지 않았다(잠금 차단 0회). 잠금은 따로 직접 시험해서 동작을 확인했다.
