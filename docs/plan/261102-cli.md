### Problem
- 도구마다 설치법이 다르다(npm, curl 설치기, AUR, go install). 어떤 도구가 어디에 어떤 검증으로 설치됐는지 한눈에 볼 수 없다.
- 공급망 검증이 없다. `curl | bash`, 서명 없는 tgz, 방금 올라온 npm 버전을 그대로 받는다.
- 에이전트가 "무엇이 빠졌는지"를 기계가 읽는 형태로 알 방법이 없다(조사 문서 §11-4가 `doctor` 스크립트를 제안만 하고 만들지 않았다).
- 대상: 이 PC의 사용자와 post-dock 개발 에이전트. 지금 필요한 이유: post-dock P1이 litestream·aws를 요구한다.

### Outcome
- `cli install <name>`이 게이트(출처·체크섬·서명·cooldown)를 통과한 도구만 설치하고, 통과 못 하면 설치 없이 이유를 보여주며 종료한다.
- `cli remove`, `cli update [--check]`가 기록된 항목만 지우고 교체한다. update는 이전 버전으로 되돌릴 수 있게 남긴다.
- `cli audit`이 `osv-scanner`로 설치된 도구의 알려진 취약점을 보고하고, 목록 자체의 정책 위반(고정 안 된 버전, 허용 안 된 호스트)을 잡는다.
- `cli doctor --json`이 도구별 설치 여부, 버전, 인증 환경변수 이름 존재, 읽기 전용 프로브 결과를 내고, 미설치 목록이 문서 §12와 일치한다.
- 인자 없이 `cli`를 실행하면 화살표 picker가 뜬다. TTY가 아니면 `--yes` 없이는 오류로 끝난다.

## 2. 구조 — proto는 설치·잠금, `cli`는 게이트·점검
```text
cli <list|install|remove|update|audit|doctor>
├─ manifest   tools.toml 읽기·검증 (이름, 방식, 출처, 버전, 해시, env, probe)
├─ resolve    후보 버전 조회 + cooldown 판정 (GitHub API / Go proxy / crates.io / bun)
├─ verify     체크섬·sha256 고정·GPG(aws)·서명(.sig) 검증, 검증 수준 기록
├─ engine     release·vendor → proto plugin add / proto install --pin global
│             bun → bun add -g,  go → go install,  cargo → cargo install --locked
├─ lock       ~/.local/state/cli/lock.json (+ proto .protolock 교차 대조)
├─ doctor     설치·버전·PATH 충돌·env 이름·프로브·런타임 의존성
└─ audit      목록 정책 점검 + osv-scanner
```
왜 이렇게: proto가 이미 다운로드, 압축 해제, 심 생성, 버전 고정, 체크섬 락, 삭제를 한다. `cli`가 그것을 다시 만들면 코드가 늘고 두 곳의 상태가 어긋난다. proto에 없는 것(cooldown, GPG, sha256 직접 고정, 취약점 스캔, 통합 점검, bun·go·cargo 경로)만 `cli`가 맡는다.

## 3. 설치 경로별 동작
| 방식 | 대상(시드) | 엔진 | 설치 위치 | cooldown 판정 | 검증 |
|---|---|---|---|---|---|
| release | litestream, xurl, goat, ovhcloud, osv-scanner, ant | proto TOML 플러그인(`~/.local/share/cli/plugins/<name>.toml`) | `~/.proto/tools`, 심 | GitHub 릴리스 `published_at` | `checksums.txt`, goat는 `.sig` |
| vendor | aws, gcloud, oauth2l | proto TOML 플러그인(vendor URL) | 위와 같음 | 버전 출처의 게시 시각(aws·gcloud는 GitHub 태그/문서, A5·A6에서 확정) | 고정 sha256, aws는 GPG 서명도 |
| bun | cf, creem | `bun add -g --minimum-release-age=604800` | `~/.bun/bin` | bun이 직접 | npm provenance 증명 확인(cf는 있음), 고정 버전 |
| go | 시드 없음(방식만 지원) | `go install <module>@<ver>` | `GOBIN=~/.local/bin` | Go 모듈 프록시 `.info`의 Time | 모듈 sumdb(기본값), 버전 고정 |
| cargo | 시드 없음(방식만 지원) | `cargo install --locked --root ~/.local` | `~/.local/bin` | crates.io API `created_at` | `--locked`, 버전 고정 |

bun 경로의 이유: bun은 proto 관리 런타임이다(`proto bin bun`). `proto`의 `npm:` 백엔드는 npm을 한 벌 더 쓰게 만들고, `bun add`는 의존성의 lifecycle script를 기본으로 실행하지 않는다(bun 도움말, 261102 확인). `~/.bun/bin`은 이미 PATH에 있다.

## 4. 상태와 잠금
proto 락파일은 `settings.unstable-lockfile`이 켜진 **로컬** `.prototools`의 옆에만 생기고, 전역 `~/.proto/.prototools`에서는 생기지 않는다(261102 임시 `PROTO_HOME` 실험). 그래서 전용 폴더를 둔다.

| 저장소 | 기록 | 용도 |
|---|---|---|
| `~/.local/share/cli/.prototools` (내용은 `[settings] unstable-lockfile = true` 한 줄) + `.protolock` | proto가 쓰는 체크섬 | release·vendor의 독립 증거. `cli`가 읽기만 한다. `cli`는 이 폴더를 cwd로 `proto -c upwards-global install <name> <ver> --pin global`을 실행하므로 레코드는 이 락파일에 남고 실제 핀은 전역에 들어간다 |
| `~/.proto/.prototools` (전역) | 플러그인 등록(`proto plugin add --to global`)과 버전 핀 | 심이 어느 폴더에서나 같은 버전을 쓰게 함 |
| `~/.local/state/cli/lock.json` | 도구별: 방식, 버전, 출처 URL, 아티팩트 sha256, 설치된 바이너리 경로, 검증 수준, 설치 시각 | remove 대상 판정, doctor·audit 입력, 이전 버전 복원 |
| `~/.local/state/cli/prev/<name>/` | 업데이트 직전 바이너리 | 롤백 |

주의: `proto uninstall`은 락파일 레코드와 전역 핀을 함께 지운다. 전역 설정은 항상 신뢰되므로 `proto trust`가 필요 없고, 전용 폴더의 설정에는 신뢰가 필요한 항목을 넣지 않는다.

교차 대조: vendor 도구는 `cli`가 먼저 파일을 받아 sha256(과 GPG)을 검증한 뒤 proto가 다시 받는다. 설치 후 `.protolock`의 체크섬이 `cli`가 검증한 값과 다르면 설치를 되돌리고 코드 2로 끝난다(검증 후 교체 공격 방어).

## 5. 게이트 정책
| 검증 수준 | 조건 | 처리 |
|---|---|---|
| sig | GPG·서명 파일 검증 성공(aws, goat) | 통과 |
| checksum | 릴리스가 낸 체크섬 파일과 일치 | 통과 |
| pinned | tools.toml의 sha256과 일치 | 통과. 최초에는 `cli`가 해시를 보여주고 사용자가 승인하면 tools.toml에 기록 |
| 없음 | 위 셋 다 없음 | 차단 |
| 공통 | 게시 후 7일 미만, 출처 호스트가 목록에 없음, 해시 불일치 | 차단. 코드 2 |

판정 예(eval 픽스처로 쓴다):

| 입력 | 결과 | 이유 |
|---|---|---|
| litestream 0.5.17, 체크섬 일치, 게시 10일 | 설치 | checksum, cooldown 통과 |
| 같은 버전, 게시 2일 | 차단 | cooldown |
| xurl, `checksums.txt` 내용이 바뀜 | 차단 | 해시 불일치 |
| gcloud, tools.toml에 sha256 없음 | 승인 요청 후 기록, 거절하면 차단 | pinned 최초 승인 |
| 출처가 목록에 없는 URL | 차단 | 호스트 허용 목록 |

## 6. tools.toml 모양

method = "release"

## 7. 명령
| 명령 | 동작 | 확인 |
|---|---|---|
| `cli` | picker로 도구·동작 선택. 비TTY면 안내 후 오류 | — |
| `cli list [--json]` | 목록 + 설치 상태 | 없음 |
| `cli install <name…>` | 게이트 → 설치 → lock 기록 → 사후 검증 | 승인 |
| `cli remove <name>` | lock에 기록된 파일과 proto 항목만 삭제 | 승인 |
| `cli update [name] [--check]` | 후보 조회·게이트. 교체 시 이전 바이너리 보관 | `--check`는 없음, 교체는 승인 |
| `cli audit [--json]` | 목록 정책 + `osv-scanner` (Go 바이너리는 `go version -m`로 모듈 추출) | 없음 |
| `cli doctor [--json]` | 도구별 상태. 종료 코드 1이면 문제 있음 | 없음 |
| 공통 | `--yes`, `--dry-run`, `--json`, `NO_COLOR` 존중 | — |

되돌리기: install은 실패 시 즉시 롤백. update는 `prev/`에서 복원(`cli update <name> --rollback`). remove는 되돌릴 수 없으므로 승인 문구에 삭제 경로를 모두 보여준다.

## 8. 기존 도구 재설치 (cf, creem, ovhcloud, osv-scanner)
- 순서: 새 방식으로 먼저 설치·검증한 뒤 옛 설치를 지운다. osv-scanner는 audit가 쓰므로 새 것이 확인되기 전에 옛 것을 지우지 않는다.
- 지우는 것: cf·creem은 proto node 전역 npm 설치(`npm uninstall -g`), ovhcloud·osv-scanner는 `~/.local/bin`의 바이너리. 로그인 정보와 설정 파일(`~/.config` 등)은 건드리지 않는다.
- 실행 직전에 삭제 목록을 보여주고 다시 승인받는다.

## 9. 단계
| 단계 | 범위 | 테스트 |
|---|---|---|
| P1 뼈대 | `dev/cli.sh`, 크레이트(`args`, `color`, `select`, `manifest`), tools.toml 시드, `cli list`, `--help`, cmd-links 행 | `cargo test`(manifest 파서·중복 이름·잘못된 방식), `cli list --json`, pty `--help` 색 |
| P2 게이트 (구현됨) | `checksum`, `cooldown`, `verify`(GPG), `http`(호스트 허용·리다이렉트 검사), `resolve`(게시 시각), `gate`(검증 수준 결정) | 변조·cooldown·호스트 픽스처 7건 이상, 로컬 HTTP 서버로 통합 테스트 |
| P3 release·vendor 설치 (구현됨) | 플러그인 TOML 생성, `proto plugin add`·`proto install --pin global`, `.protolock` 교차 대조, lock.json, remove, dry-run | 임시 `PROTO_HOME`에서 litestream 설치·삭제 왕복, 체크섬 불일치 롤백 |
| P4 bun·go·cargo (구현됨) | 세 엔진, 각 cooldown 판정 | 임시 홈에서 설치·삭제, 판정 단위 테스트 |
| P5 doctor (구현됨) | 상태·PATH 충돌·env 이름·프로브·런타임 의존성·`--json` | §12 미설치 목록 대조, env 없을 때 `skipped` |
| P6 audit (구현됨) | 목록 정책 점검, `osv-scanner` 연동, Go 모듈 추출 | 알려진 취약 모듈 픽스처로 코드 2 |
| P7 update·picker (구현됨) | `--check`, 교체, 롤백, 화살표 picker | pty 키 입력(Enter, j+Enter, q, Ctrl-C), 롤백 왕복 |
| P8 이행 (구현됨) | 기존 도구 재설치(§8), 조사 문서 §11-4·§12·§13 갱신 | 재설치 후 `doctor --json` 전부 설치, 옛 경로 없음 |

선후 관계: P1 → P2 → P3 → (P4, P5 병행 가능) → P6 → P7 → P8. P3은 P2의 게이트 위에서만 설치하므로 P2 없이 먼저 만들지 않는다.

공통 완료 조건(단계마다): `cargo test` 통과 → 릴리스 빌드 경고 없음 → 해당 명령을 임시 홈에서 실행해 결과 확인 → `cmd-links apply cli`로 PATH 실행 확인 → 사용자 확인. 시크릿 값은 어느 출력에도 나오지 않는다.

정지 규칙: 테스트가 실패하거나 동작이 이 플랜과 다르면 그 단계를 멈추고 보고한다. 플랜과 다른 사실이 나오면(§확인할 가정) 구현을 계속하기 전에 플랜을 먼저 고친다.
