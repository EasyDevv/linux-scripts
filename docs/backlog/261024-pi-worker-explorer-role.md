# Explorer 역할과 Quick 티어 검토 (BulkRead 비교)

질문: dashboard `/settings/models`에 Explorer 역할을 넣을지, 그리고 worker가 기본 Standard 대신 Quick을 써도 되는지.
재현: `bun ~/.agents/plugins/pi/evals/explore.ts --runs 3` (통제 벤치), `bun evals/explore-orch.ts --runs 2` (Sonnet 오케스트레이터). 결과는 `~/.cache/pi-worker-evals/explore*.jsonl`.

## 확인한 사실

- dashboard Models 화면의 역할은 Worker, Lead 둘뿐이다. 각 역할은 quick~premium 범위를 갖고, 작업 demand에 따라 티어가 정해진다.
- pi 쪽 `tiers.json`에서 quick, standard, high는 같은 모델(`deepseek-v4.1-flash`)이고 thinking만 low, high, max로 다르다.
- `mcp__pi__worker`는 `standard`와 `high`만 받는다. Quick은 worker 경로로는 호출할 수 없다.

## 시나리오 (정답은 스크립트로 계산)

읽기 전용 fixture(`~/.pi/agent/extensions` 복사본 29개 항목, `~/.agents/skills-routed` 복사본 SKILL.md 40개). 답은 한 줄에 이름 하나, 마지막에 `COUNT n`.

| id | 묻는 것 | 함정 |
|---|---|---|
| commands | `registerCommand`를 호출하는 소스 9개 | 테스트와 주석에도 단어가 나온다 |
| env | `PI_SUBAGENT` 자체를 쓰는 파일 12개 | `PI_SUBAGENT_DEPTH` 등 접두사 변수 |
| untested | 테스트가 없는 최상위 항목 | 없는 것을 찾기 |
| long | 150줄 초과 SKILL.md 7개 | 40개를 세어야 하고 3단계 깊이 파일이 있다 |

| drift | 30개 설정 파일에서 어긋난 값 8개 (파일:키) | 순서, 주석, 공백만 다른 방해 파일 |

drift는 읽고 비교하는 일을 재려고 나중에 추가했다. 파일 30개, 파일당 62줄이고, 정답은 심어 둔 값이다(`evals/explore.ts`가 생성).

## 통제 벤치 (6개 구성 × 4 시나리오 × 3회 = 72회)

구성: q/s = quick(low)/standard(high), v/s = vague/structured 지시문, r = 읽기 전용 도구(read, grep, find, ls).

| 구성 | 정확 | 중앙값 | 총비용 | 평균 tool call |
|---|---|---|---|---|
| qv | 12/12 | 11.9 s | $0.029 | 3.8 |
| qs | 12/12 | 12.0 s | $0.028 | 4.6 |
| sv | 12/12 | 11.5 s | $0.030 | 4.2 |
| ss | 12/12 | 12.0 s | $0.030 | 4.8 |
| qsr (제안한 Explorer) | 12/12 | 14.0 s | $0.053 | 19.8 |
| ssr | 11/12 | 21.2 s | $0.055 | 25.8 |

`long`은 structured 지시문의 범위 문구를 고친 뒤 3회 다시 돌린 값이다. 고치기 전 결과는 아래 "지시문" 항목에 있다.

|---|---|---|---|---|

## 해석

- **Quick과 Standard는 이 종류의 일에서 차이가 없다.** 정확도, 시간, 비용 모두 같다. thinking 단계가 결과를 바꾸는 일이 아니었다. 오답은 전부 티어가 아니라 지시문이나 형식에서 나왔다.
- **지시문이 티어보다 크다.** 처음 `long` structured 구성이 일관되게 1개를 놓쳤다. 지시문의 "두 단계 깊이"라는 가정이 3단계 깊이의 `system/android-cli/base`를 범위 밖으로 잘랐기 때문이다. worker는 지시를 충실히 따랐고, 틀린 가정이 그대로 누락이 됐다. vague 지시문의 standard 한 번은 상위 디렉터리까지 뒤져서 경로 접두사가 붙은 답을 냈다.
- **읽기 전용 도구는 오히려 손해다.** bash가 없으면 줄 수를 세려고 파일을 하나씩 읽는다(`long`에서 tool call 50~80회). 비용 약 2배, 시간 약 1.5~2배, ssr은 1건 틀렸다. 읽기 전용은 도구 제거가 아니라 지시문("파일을 바꾸지 말 것")이나 guard로 거는 편이 낫다.
- **작은 조사는 위임하는 쪽이 더 느리다.** Sonnet은 질문만 받으면 worker를 한 번도 부르지 않았고(0/8) 직접 10초에 끝냈다. 위임을 지시하면 31초로 3배 걸렸고 총비용도 약 16% 올랐다. worker 자체 비용은 $0.003 안팎이지만 오케스트레이터가 브리핑을 쓰고 보고를 읽는 비용이 더 크다. 이 시나리오들은 grep 몇 번으로 풀리는 일이다.

## 결정 후보

1. **Explorer 역할은 지금 추가하지 않는다.** 근거: Quick 이득이 측정되지 않고, 읽기 전용 도구는 손해이고, 역할 하나는 레이어 하나다. 이득이 확인되면 그때 다시 본다.
2. **Quick을 쓰고 싶다면** worker의 `WORKER_TIERS`에 `quick`을 추가하는 한 줄이 먼저다. 읽기 위주 작업에서 같은 품질이다.
3. **위임 기준 문구**: grep 몇 번으로 끝나는 질문은 직접 한다. 위임은 내용 전체를 읽어야 하는 큰 읽기, 또는 다른 일과 겹쳐 돌릴 때만 한다.
4. **브리핑 규칙**: 범위는 "어느 깊이까지"를 가정하지 말고 "하위 전체"로 쓴다. 출력은 경로 기준과 형식을 명시한다.

## 적용 (pi 0.3.1)

- 결정 후보 2, 3, 4를 적용했다. `quick` 티어 추가(`/worker` 상태에도 표시), 위임 지시(`DELEGATION`)에 "grep, wc 한두 번으로 풀리는 질문은 직접" 추가, 브리핑 규칙(범위는 하위 전체, 경로 기준과 출력 형식 명시, 읽기 전용 조사는 quick과 shell 유지) 추가.
- 위임 평가: 변경 전 `r4` 12/12, 변경 전 코드로 돌린 `r5` 10/12, 변경 후 `r6` 10/12. s10-mixed는 `r5`(변경 전)와 `r6` 모두 실패해서 변경과 무관한 변동으로 본다(두 일을 한 번에 나누지 않고 worker 하나에 합쳐 맡김).
- 바뀐 것은 s01-search 하나다. 변경 전에는 worker에 맡겨 50초, 변경 후에는 Grep 3번과 Read 3번으로 직접 24초에 풀었고 비용도 $0.166에서 $0.152로 줄었다. 평가는 "worker를 불러야 한다"고 기대해서 FAIL로 찍지만, 벤치 결과(직접이 더 빠르다)와 일치하는 의도된 변화다. 평가 기대치는 바꾸지 않았다.

## 읽고 비교하는 일 (drift, 추가 측정)

통제 벤치(구성 6개 × 3회): 18회 모두 정확했다. bash가 있는 구성(qv, qs, sv, ss)은 중앙값 약 9~15초, 건당 $0.001~0.003이었다. 읽기 전용 구성(qsr, ssr)은 도구 호출 37~103회, 44~267초, $0.007~0.026으로 5~10배 비쌌다.

Sonnet 오케스트레이터(3회): direct, natural(worker 0회 호출), explicit 모두 8/8 정확했다.

| arm | 중앙값 | 평균 비용 |
|---|---|---|
| direct | 13.6 s | $0.077 |
| natural | 13.9 s | $0.080 |
| explicit (worker) | 52.0 s | $0.080 |

- 파일을 많이 읽는 일도 Sonnet이 `sort`와 `diff` 같은 명령으로 직접 풀어서 출력이 작다. 그래서 위임해도 오케스트레이터 컨텍스트를 아끼지 못했고 비용은 같았다. 시간만 4배 걸렸다.
- explicit에서 Sonnet이 고른 티어는 high 2번, quick 1번이었다. 읽기 전용 조사에 quick을 쓰라는 안내를 도구 설명에 넣었지만 아직 따르지 않는다.
- 결론은 그대로다. Explorer 역할을 둘 근거가 없다. 이 환경에서 읽기 중심 일은 직접 하는 쪽이 같은 비용에 4배 빠르다.

## 한계

- 시나리오 5개가 모두 grep, `wc`, `diff` 같은 명령으로 풀리는 일이다. 사람이 읽어야 풀리는 의미 비교(문서 해석, 설계 판단)는 정답을 스크립트로 만들 수 없어 측정하지 못했다.
- 통제 벤치 3회, 오케스트레이터 2회다. 모델은 deepseek-v4.1-flash 하나다.
- 통제 벤치는 구성 6개를 동시에 시작해 같은 부하를 받게 했지만, 한 번(`long` qv)은 129초까지 튀었다. 중앙값으로 보았다.
- Sonnet 비용은 이 환경의 시스템 프롬프트와 도구 정의 때문에 직접 풀어도 건당 약 $0.06~0.10이다.
