# 🏗️ executor 코드를 더 똑똑하게 정리한 이야기

> 초보 개발자도 이해할 수 있게 쉽게 썼어요.
> "아키텍처 리팩토링"이 뭔지, 왜 했는지, 어떤 원칙으로 했는지를 설명합니다.

---

## 1. 예전 코드는 왜 문제였을까?

예전 executor 코드는 9개의 작은 파일로 나뉘어 있었어요. 그런데 파일이 작다고 항상 좋은 건 아니에요.

### 문제 1: 파일이 너무 얕았다 (Shallow module)

**"얕은 모듈"** 이란, 파일을 사용하려면 파일 안에 뭐가 들었는지 거의 다 알아야 하는 경우를 말해요.

예를 들어 `config.ts`는 무려 **14개**나 되는 함수를 밖으로 내보내고 있었어요.  
이 함수들을 사용하는 쪽에서는 뭘 써야 할지 매번 14개 중에 골라야 했죠.

> 🧸 **비유:** 문구점에 가서 연필 한 자루 사려고 하는데, 점원이 "연필, 샤프, 볼펜, 싸인펜, 크레파스, 형광펜…"을 하나하나 설명해야 하는 상황이에요. 그냥 "연필 주세요" 하면 되는 건데 말이죠.

### 문제 2: 비슷한 일이 여기저기 흩어져 있었다 (Scattered logic)

한 가지 일을 이해하려면 여러 파일을 봐야 했어요.

예를 들어 **"인스턴스가 진짜 켜졌는지 확인"** 하는 일 하나만 봐도:

- `commands.ts`에서 "뭐가 ready pattern이지?" 하고 준비하고
- `journal.ts`에서 "로그에 ready라고 나왔나?" 확인하고
- `runtime.ts`에서 "포트가 열렸나?" 확인하고

이렇게 3개 파일을 넘나들며 봐야 했어요.

> 🧸 **비유:** 라면을 끓이는데, 냄비는 주방 A에서 찾고, 물은 주방 B에서 받고, 가스레인지는 주방 C에 있어요. 하나만 하면 되는데 세 군데를 돌아다녀야 하는 거예요.

### 문제 3: JSON 데이터가 여기저기 샜다 (Leaky abstraction)

설정 파일의 원본 데이터를 `JsonObject`라고 불렀는데, 이 타입이 온갖 파일에 퍼져 있었어요.

`config.ts`, `commands.ts`, `runtime.ts`, `journal.ts`, `supervisor.ts` — 모두가 설정 파일이 "그냥 JSON 덩어리"라는 걸 알고 있었어요.

> 🧸 **비유:** 냉장고에서 우유를 꺼낼 때마다 "이 우유는 2026년 5월 26일에 OO목장에서 생산되었고, 유통 과정은…"을 매번 설명해야 하는 거예요. 그냥 "우유 주세요" 하면 되는데!

## 2. 우리가 적용한 원칙들

코드를 고치면서 몇 가지 중요한 원칙을 적용했어요.

### 원칙 1: 깊은 모듈 (Deep module)

**"깊은 모듈"** 이란, 겉으로 보이는 인터페이스는 작고 간단한데, 그 안에서 하는 일은 많은 모듈을 말해요.

| 구분 | 얕은 모듈 (전) | 깊은 모듈 (후) |
|---|---|---|
| `config.ts` | 14개 함수 외부 노출 | `readConfig()`, `writeConfig()` 단 2개 |
| `runtime.ts` | 14개 함수 외부 노출 | 아예 사라짐 (`process-manager.ts`에 흡수) |

> 🧸 **비유:** 리모컨을 생각해보세요. 리모컨에는 전원, 볼륨, 채널 버튼만 있어요. 그 안에는 수백 개의 부품이 있지만, 우리는 버튼만 누르면 돼요. 그게 깊은 모듈이에요.

### 원칙 2: 인터페이스 = 테스트 표면 (Interface is test surface)

모듈의 인터페이스가 곧 테스트 대상이에요. 내부 구현이 어떻게 되어 있는지는 테스트에서 알 필요가 없어요.

예를 들어 `config.ts`를 테스트할 때는 `readConfig()`가 올바른 `NormalizedConfig`를 돌려주는지만 확인해요. 내부에서 JSON을 어떻게 파싱하는지는 테스트하지 않아요.

> 🧸 **비유:** 커피머신이 "내부에서 물을 95도로 가열하는지"는 신경 쓰지 않고, "커피가 잘 나오는지"만 확인하는 거예요.

### 원칙 3: 소멸 테스트 (Deletion test)

"이 모듈을 통째로 지우면 어떻게 될까?" 하고 상상해보는 거예요.

- **얕은 모듈** = 지우면 그냥 사라짐 (아무 일도 안 하던 거니까)
- **깊은 모듈** = 지우면 그 일을 하던 복잡함이 다른 곳에서 다시 나타남

예를 들어 `runtime.ts`를 지우면, 거기 있던 PID 파일 읽기, `ps` 명령어 실행, `lsof` 호출이 전부 `commands.ts`와 `supervisor.ts`로 퍼져나가야 했어요. 즉 `runtime.ts`는 나름대로 일을 하고 있었던 거예요.

### 원칙 4: 한 군데에 모아라 (Locality)

같은 종류의 변경이 필요한 코드는 한 파일에 모여 있어야 해요.

- **전:** 포트 충돌 감지가 `commands.ts`와 `journal.ts`에 퍼져 있었음
- **후:** 모든 readiness 로직이 `readiness.ts` 한 곳에 모임

> 🧸 **비유:** 장난감을 방 여기저기에 흩어놓으면 치울 때 힘들잖아요? 장난감 통 하나에 다 모아두면 한 번에 치울 수 있어요.

## 3. 우리가 실제로 한 일

### Phase 1: Config 모듈 깊게 만들기

**무엇을 했나요?**

- `config.ts`의 14개 함수를 `readConfig()`와 `writeConfig()` 단 2개로 줄였어요.
- `JsonObject` (원본 JSON 데이터)가 다른 파일로 새는 걸 막았어요.
- `NormalizedConfig`에 편리한 메서드(`getInstance`, `isEnabled`, `getPort` 등)를 추가했어요.

**결과:**

- 다른 파일들은 "설정 파일이 내부에서 어떻게 생겼는지" 몰라도 돼요.
- 설정 파일 형식이 바뀌면 `config.ts`만 고치면 돼요.
- `config.test.ts`에서 11개의 테스트가 동작해요.

### Phase 3: Process Manager 만들기

**무엇을 했나요?**

- `runtime.ts`(242줄)를 통째로 `process-manager.ts`로 옮겼어요.
- `supervisor.ts`에 흩어져 있던 프로세스 시작/종료 로직도 같이 옮겼어요.
- `ProcessManager`라는 클래스를 만들어서 깔끔한 인터페이스를 제공했어요.

**결과:**

- `supervisor.ts`가 무슨 인스턴스를 실행할지"만 결정해요 (HOW가 아니라 WHAT).
- 프로세스 관리(시작, 종료, PID 파일, 포트 검사)는 `ProcessManager`가 다 해요.
- `runtime.ts` 파일이 완전히 사라졌어요!

### Phase 2: Readiness 모듈 만들기

**무엇을 했나요?**

- 인스턴스가 "진짜 준비됐는지" 확인하는 로직을 `readiness.ts`로 모았어요.
- Vite(프론트엔드 도구) 관련 특수 코드는 `vite-adapter.ts`로 분리했어요.
- `journal.ts`는 로그 보여주기와 서비스 제어만 하도록 가볍게 만들었어요.

**결과:**

- "준비됐나?" 확인하는 로직이 한 곳에 있어요. 언제 수정해야 할지 바로 알 수 있어요.
- Vite 말고 다른 도구를 쓰게 되어도 Readiness 모듈은 안 고쳐도 돼요.
- `journal.ts`가 376줄에서 110줄로 줄었어요!

## 4. 정리: 파일 구조 변화

**전:**

```
executor/
  config.ts     (308줄, 14개 export)
  runtime.ts    (242줄, 14개 export)
  journal.ts    (376줄, 로그 + readiness + service)
  supervisor.ts (278줄, 오케스트레이션 + 프로세스 관리)
  commands.ts   (CLI 명령어)
  types.ts      (6개 타입)
  utils.ts      (잡다한 유틸)
  main.ts       (진입점)
```

**후:**

```
executor/
  config.ts          (config read/write만)
  process-manager.ts (runtime + supervisor 프로세스 로직)
  readiness.ts       (readiness 폴링 + 포트 충돌 처리)
  vite-adapter.ts    (Vite 전용 어댑터)
  journal.ts         (로그 표시 + service 제어만, 110줄)
  supervisor.ts      (오케스트레이션만, 70줄)
  commands.ts        (CLI 명령어)
  types.ts           (정규화된 타입만)
  utils.ts           (잡다한 유틸)
  main.ts            (진입점)

  config.test.ts     (11개 테스트)
```

이제 각 파일이 하는 일이 명확해졌어요.  
파일 이름만 봐도 "아, 이 파일은 이런 일을 하는구나!" 알 수 있죠?
